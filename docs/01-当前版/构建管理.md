# 构建管理（2026-11-18 起）

这份文档说明整理助手的构建为什么会被「管起来」、管在哪、出问题怎么处理。
管理代码只有一份：`tools\build-manager.ps1`，由 `build.ps1` 在开头点源加载。

## 为什么要有它

2026-11-18 凌晨实际发生的事：

- 00:57:30 会话 A 启动构建，把版本写成 `1.23.15`，开始编译；
- 01:02:14 会话 B 又启动构建，把版本写成 `1.23.16`，此时 A 的 rustc 还在链接；
- 01:04:37 A 产出 exe 和 `TidyAssistant_1.23.15_x64-setup.exe` 收工。

结果：根目录 exe 内嵌 `1.23.15`，配置文件写着 `1.23.16`，release 里躺着 1.23.15 的包。
谁都不知道现在跑的到底是哪份源码，也没法回滚——因为改动从来没进过版本库。

根因不是某个人手滑，是**构建没有互斥、没有快照、没有台账**。所以补上这三件事。

## 一条命令看状态

```powershell
.\build.ps1 -Status
```

输出包含：配置版本、Cargo 版本、当前源码 SHA 与未提交文件数、运行副本的内嵌版本与大小、
构建锁占用、正在跑的编译进程、release 清单、最近几次构建、一致性结论。

一致性有问题的典型提示：

| 提示 | 含义 | 处理 |
|---|---|---|
| `exe 内嵌版本 X ≠ 配置版本 Y` | 构建没跑完，或产物没覆盖 | 重新 `.\build.ps1` |
| `版本源不一致` | `tauri.conf.json` 与 `Cargo.toml` 被手改岔了 | 用 `-Bump` 或 `-Version` 重写，别手改 |
| `有构建进程在跑` | 有会话正在编译 | 等它结束，不要并行 |
| `构建锁被占用` | 另一个走 build.ps1 的构建持锁 | 等；确认进程死了再看下一节 |

只看不改时也可以直接跑模块自检（有问题退出码 1，适合给脚本用）：

```powershell
pwsh -NoProfile -File tools\build-manager.ps1 -Check
```

## 机制一：构建锁（同一时间只允许一个构建）

- 锁文件：`D:\Builds\.locks\tidyassistant.build.lock`（纯 ASCII，不放仓库里）。
- 内容：`pid`、`startTicks`、`session`、`version`、`mode`、`startedAt`、`host`、`command`。
- 创建方式：`CreateNew` 原子创建，两个进程同时抢只有一个能成功，另一个直接报错退出。
- 判活：PID 存在**且**进程启动时间对得上才算活着（防 PID 复用）。
- 崩溃残留：PID 已死的锁会被自动改名成 `.stale-<时间戳>` 并继续，不需要手工删。
- 拿不到锁时**不排队、不等待**：打印持锁会话、PID、版本、开始时间后退出。排队会让两个构建前后脚覆盖同一个 exe，比失败更糟。

### 兜住「不走 build.ps1 的旧会话」

锁只能约束走 `build.ps1` 的构建。为了兜住直接调 `cargo-tauri` / `cargo` 的会话，
启动前会扫描进程命令行里同时含 `tidyassistant` 与 `cargo|cargo-tauri|rustc` 的进程，
发现就拒绝启动并列出 PID 和命令行。2026-11-18 之前的会话都是这种，所以这一步是必要的。

## 机制二：构建前源码快照（产物永远追得回源码）

仓库就是源码树本身：`D:\Tools\TidyAssistant\.git`，只跟踪文本源码与文档。

- `.gitignore` 忽略：`tidy-assistant.exe`、`引擎\`、`release\`、`tools\cargo-tauri.exe`、
  `src\src-tauri\target\`、`src\engine\indexwalk.exe`、`.build\`、`*.pdb`、`*.log`。
- 构建拿到锁之后、动手编译之前，执行：
  1. `git add -A`
  2. `git commit -m "pre-build <版本> (<模式>)"` —— **包含其他会话尚未提交的改动**
  3. 打标签 `build-<版本>`
  4. 把短 SHA 写进台账
- 如果 `git add` 与 `commit` 之间又有人改了文件，会补一次 `[cont]` 提交，确保快照完整。
- 意义：某次构建的产物出问题时，`git show build-1.23.17` 就能看到它到底由哪份源码生成；
  被人覆盖、误删也能从提交里恢复。

注意：`引擎\` 与 `release\` 是产物不是源码，不进 git；引擎由 `src\engine\` + spec + venv 决定。
需要精确定位引擎产物时看台账里的版本与构建时间，配合 `src\engine` 的对应提交。

## 机制三：构建台账

每次构建（成功或失败）追加一行 JSON：

- `D:\Builds\tidyassistant-builds.jsonl`（跨仓库、长期）
- `D:\Tools\TidyAssistant\.build\builds.jsonl`（跟着仓库走）

字段：`version`、`kind`（`bump:patch` / `explicit` / `none`）、`mode`（`app` / `engine` / `portable`）、
`session`、`result`（`ok` / `failed`）、`git`（源码快照 SHA）、`exe`（SHA256）、`exeBytes`、
`releases`（包名 + SHA256）、`duration`、`note`、`startedAt`、`host`。

台账用来回答三个问题：这个版本是谁构建的、用的是哪份源码、产出的二进制哈希是多少。
如果同一版本号出现两份不同 exe 哈希，构建结束时会黄色告警——版本规范禁止这种事。

## 构建后自检（不通过就判失败）

`build.ps1` 在收工前统一检查，任一条不满足直接抛错，不会打印「已完成」：

1. `tauri.conf.json` 与 `Cargo.toml` 的版本一致；
2. 根目录 `tidy-assistant.exe` 的内嵌版本等于配置版本（只构建引擎/只打便携包时跳过）；
3. `-Bundle` 时 `release\TidyAssistant_<版本>_x64-setup.exe` 必须存在；
4. `-Portable` 时 `release\整理助手_<版本>_便携版.zip` 必须存在；
5. 没有别的构建进程在跑。

## 冲突与故障处理

| 情况 | 做法 |
|---|---|
| `-Status` 显示锁被占 | 等持锁会话结束；不要删锁 |
| 持锁进程已经不在了 | 不用管，下次构建会自动把锁判死并改名 `.stale-*` |
| 持锁进程还在但卡死 | 先确认它不是真的在编译（看 cargo/rustc 是否在推进），再结束该进程；锁会在下次构建时被判死 |
| 发现有旧会话直接跑 cargo | 让它跑完再构建；同时提醒对方以后走 `build.ps1` |
| 构建中途失败 | 看红字和台账 `note`；源码快照已提交，`git checkout <SHA>` 可回到构建前状态 |
| 产物版本对不上 | `git log` 找 `pre-build` 提交，确认是构建被中断还是产物没覆盖，然后重新构建 |

## 回滚

```powershell
git -C D:\Tools\TidyAssistant log --oneline --decorate -20   # 看 pre-build / build-<版本>
git -C D:\Tools\TidyAssistant show build-1.23.17             # 看某次构建的源码
git -C D:\Tools\TidyAssistant checkout <SHA> -- src          # 只回滚源码
```

二进制不进 git，回滚二进制靠 `release\` 里的历史包（只留两份）或 `release\archive\`。
需要长期留存的包请手工放进 `release\archive\`。

## 已知边界

- 锁是**单机文件锁**，不跨机器；本机多会话共享 `D:\Builds`，所以有效。
- 快照发生在构建前：构建期间别人再改源码，这次产物不包含那些改动，需要再构建一次；
  `-Status` 的「未提交变更」和 git 状态能看出来。
- 引擎产物（`引擎\`）目前只按版本+源码快照追溯，没有逐文件哈希。
- 前端无打包步骤，`src\web` 改完直接进构建，不存在独立的前端产物。
