# 索引新鲜度：第一性原理重推 + 红队审查 + 最终方案

版本：1.42.3 ｜ 日期：2026-11-20 ｜ 对应变更记录 1.42.0 / 1.42.2 / 1.42.3

这份文档回答三个问题：抛开现有做法从头推一遍，索引该长什么样；用最强反对者的角度攻击这个设计，哪些地方会漏；最后给出修正后的方案，以及为什么剩下的问题不做。

---

## 一、第一性原理重推

### 1.1 把问题拆到底层

用户的原始诉求是一句话：

> 盘里面要是新增内容的话索引就是旧的了，我要是不重构索引就没办法搜到新文件数据，这要怎么设计能保证可以第一时间搜索到最新文件数据呢，并且最好可以可控不然扫磁盘次数多会伤磁盘

这句话里藏着一个未经检验的前提：**「搜到新文件」和「保持索引最新」是同一件事**。

拆开看，用户实际会问的三类问题，对新鲜度的要求差着数量级：

| 问题 | 需要什么 | 可接受的旧 |
|---|---|---|
| 「我刚下载的那个 3 GB 在哪」 | 知道**这一小片**目录的新文件 | 几乎不能旧，但只需要极小的范围 |
| 「这个文件夹里有什么」 | 读**那一个**目录 | 完全不能旧，但只需 `os.scandir` 一次，几毫秒 |
| 「什么最占空间」 | 全局体积快照 | 旧几分钟完全无所谓——体积的变化尺度是天和周 |

旧实现把三件事全部推给「索引」这一个机制，于是「什么最占空间」和「刚下载的文件」被迫共享同一个新鲜度策略。**这是设计错误，不是索引机制的错误。**

第一性原理层面的结论：新鲜度不是一个全局属性，而是「每个查询需要的范围 × 该范围变化的频率」的函数。全局统一的 TTL 一定会同时过度服务第一类问题（扫太多）和服务不足第二类问题（扫太少）。

### 1.2 「扫盘伤磁盘」这个前提不成立

这是必须先纠正的事实错误，因为它会导向完全错误的设计（拼命减少扫描次数）。

实测（Rust 遍历器 `indexwalk.exe`，只读 NTFS 目录项，不读文件内容）：

```
D:\  595,241 文件 / 75,932 目录   建库 5,281 ms
E:\  822,497 文件 / 38,894 目录   建库 2,261 ms
全量 141 万文件                    约 7.5 秒
```

而用户实际感受到的 20 秒是这样的（真实会话 `s-mwoj2j7c.json` 第一轮）：

```
top_files  20,043 ms   —— 这是 Python 单线程现扫深层目录，不是建索引
```

量级差 10 倍，但用户感觉都是「很慢」。**真实的成本是大 CPU 占用和界面无响应，不是磁盘磨损。** 一块现代 SSD 的写入寿命以 PB 计，7.5 秒的顺序目录枚举相比每天几十 GB 的正常写入可以忽略。

所以设计目标应该改写为：**让用户察觉不到**，而不是**减少扫描次数**。「可控」的正确实现是让用户能选择「什么时候被打扰」，不是「少读盘」。

### 1.3 从约束推导，而不是从现有代码推导

三条硬约束决定了可行解空间：

**约束 A：引擎是单线程 RPC 环。** `run_engine()` 严格「读一行 → 分发 → 写一行」。任何耗时操作放进查询路径，就会堵死期间所有 UI 调用。这一条直接排除了「查询时全量重扫」。

**约束 B：全盘 stat 不可行。** D 盘 75,932 个目录逐个 `os.stat` 要 **12,029 ms**。即便只读目录元数据（不是文件），也不够快。

**约束 C：索引必须能自愈。** 索引是磁盘的副本，副本必然会偏离。没有自愈机制的快照，偏离只会单调累积——这正是用户 D 库里 9/400 条记录指向已删除文件的原因。

由 A + B 得到第一个必然结论：**任何在查询路径上的新鲜度动作，其规模必须被硬性限制在一个小常数内**。300 毫秒是可行的，12 秒不是。

由 C 得到第二个必然结论：**必须有后台的、抽样的、能自己决定要不要重建的自检**。全量核对等于把建索引再跑一遍，那样自检本身就成了新的「扫盘伤磁盘」来源。

### 1.4 反推出来的分层

不是先有分层再找理由，而是三个约束各自逼出一层：

- 约束 A（不能堵查询）+ 变化最频繁的小范围 → **查询期的局部刷新**（后来叫热目录保鲜）
- 约束 C（必须自愈）+ 全盘太贵 → **后台的抽样校验**（后来叫 Tier 3）
- 写操作本来就知道自己改了什么 → **写穿**，成本为零，没有理由不做

写穿的优先性值得单独说：软件自己移动、删除、清理文件的时候，它**已经知道**哪些路径变了。这时候还让索引保持旧状态，等于明知答案却不写下来。这是整个方案里唯一「收益确定、成本为零」的一层，所以它排在最前面做。

### 1.5 被推导排除的方案

**文件监听器（`ReadDirectoryChangesW`）被排除，理由不是「实现麻烦」，而是量出来的收益太小。**

热目录（桌面/文档/下载/图片/视频）全量重建一次：

```
walker 直接跑五个热目录：214 ms
走生产的 index_add + build_index：263 ms（4,426 文件，库 0.45 MB）
稳态重跑：303 ms
```

监听器换来的是这 300 毫秒的窗口期。代价是：常驻文件句柄、热目录白名单要维护、Windows API 绑定、跨线程事件队列、漏事件时的静默不一致（监听器漏一个事件，索引就永久错一个条目，而没有任何机制能发现）。

**用一个 300 毫秒的定期重建，换掉整套监听机制，是明显的正确取舍。**

**USN 日志（`FSCTL_READ_USN_JOURNAL`）同样被排除**，理由更强：它需要管理员权限，而这软件的定位是「装给朋友用」，不能假设权限。

**必须有规模分层意识**：热目录 4,426 文件 vs 整盘 141 万文件，差 316 倍。热目录便宜不等于整盘便宜。任何把热目录的结论外推到整盘的设计都会立刻崩掉——这一点后来真的坑了我一次（见 §2.1）。

## 二、红队审查

用最强反对者的角度攻击上面的设计。以下每一条都是实际攻击成功的，不是假想。

### 2.1 攻击一（致命）：「热目录」对整盘索引的用户根本不存在

**攻击**：你说的热目录是 `C:\Users\十二\Desktop` 这些。但这个用户真实的索引范围是什么？

实测 `catalog.json`：**只有 `D:\`（595,241 文件）和 `E:\`（822,497 文件），C 盘用户目录完全不在索引里。**

于是「搜不到就补扫热目录」这条机制，补扫的是他从没索引过的 C 盘，而新文件落在 D:/E:。验收标准「第一次搜就能找到」**对真实用户完全不成立**。

**更严重的是第二层**：旧代码在这条路径上写了 `index_add(missing)`——保鲜顺手把 C 盘用户目录**加进了索引范围**。用户的占用排行会莫名多出几个 C 盘目录，而他从未同意过这件事。**「保鲜」越权成了「扩张」。**

**结果**：这条攻击成立。修法是重新定义热目录——不是「系统默认的几个用户目录」，而是「用户**已有索引范围之内**、新文件最可能落下的地方」：

1. 文件数 ≤ 20,000 的小索引根，整棵算热（用户特意只索引一个目录，那这个目录本身就是热点）
2. 大索引根（整盘）的顶层，找名字命中「下载 / Downloads / 桌面 / Desktop / 迅雷下载」的直接子目录
3. `default_index_roots()` 里**本身就落在某条索引范围之内**的（只确认在范围内，不新增范围）

并且刷新方式从 `build_index(roots=[p])` 改成新的 `_ix_refresh_subtree(db, p)`——因为前者会先 `index_add(p)` 把 `D:\下载` 登记成一条**新索引根**，对整盘用户同样是范围扩张。

**这条修完之后，我加了一条守护测试锁住不变式**：刷新前后 `_ix_load()` 的 root 列表必须完全一致。这条测试做过两轮双向验证才确认它是真的——第一次反向验证只改回外围过滤条件，测试仍绿，因为没恢复 `index_add` 那段真正造成扩张的代码。**反向验证必须恢复造成 bug 的那段代码本身。**

### 2.2 攻击二：旧格式的库永远不会自动升级，「读不懂」被当成了「没问题」

**攻击**：你说 Tier 3 抽样校验能自愈。那它怎么对待一个它读不懂的库？

`_ix_verify_one` 里是 `SELECT path, mtime, n_files FROM dirs ORDER BY RANDOM() LIMIT ?`。schema 2 的老库没有 `n_files` 列，这条 SQL 抛异常，被 `except Exception: return {"ok": True, ...}` 吞掉。

于是：**自检永远判健康、永远不重建、库永远停在 schema 2。** schema 3 的全部收益（32 ms 聚合、写穿、保鲜）对所有升级上来的老用户静默失效，而界面上一切正常。

实测确认：1.42.0 / 1.42.1 装上去之后，用户两个真实库的 `PRAGMA user_version` 仍然是 2，`dirs` 列仍然是 `['id','path','mtime','fresh','f0','n']`。

**结果**：这条攻击成立，而且是最隐蔽的一条——因为它不报错，只是什么都没发生。「读不懂」和「没问题」是两件事。读不懂要修（重建一次就升级了），不能当成没事。

**修法**：`_ix_verify_one` 先检查 `_index_has_totals(db)`，为假直接返回 `ok: False` 且 `why` 说明「索引是旧版格式（schema N），重建一次即可升级」。真机复验：`search.selfcheck` 7.9 秒把两个库从 schema 2 升到 3，用户什么都不用点。

### 2.3 攻击三：建库撞上「正在被读」就整次失败

**攻击**：Windows 上 `os.replace(staging, target)` 在另一个连接还开着 `target` 时失败。实测 `PermissionError [WinError 5] 拒绝访问`。你的建库要几十秒，期间用户随手点一下「什么最占空间」就会打开那个库——建库就白跑了？

**结果**：成立。而且失败后果被放大了一倍：`build_index` 的 `except` 分支原来会把 `item["files"] = 0` / `item["dirs"] = 0`，含义是「这个根里没东西」——**一次几十毫秒的瞬时读取，能把 82 万文件的索引在清单里改成 0 条**。

修法两件：

- `os.replace` 加 6 次退避重试（0.05 / 0.1 / 0.2 / 0.4 / 0.8 / 1.2 秒）。读的那一头通常只持有几十毫秒，让一次瞬时读取把整次建库判死，是最不合算的失败。
- 失败分支不再清零计数。失败就是「这次没建成」，旧的记数保持原样，`why` 里说清原因。

### 2.4 攻击四：两条写路径共用 `.db` 却不共用锁

**攻击**：`build_index` 走 `_index_build_one`，在 `target + ".new"` 上先删 staging 再重建最后 replace。而 `hot_refresh` 走 `_ix_refresh_subtree` 直接写活库。两条路径同时进来会怎样？

**结果**：staging 文件会被互相删掉，最后 `os.replace` 上去的可能是半个库。修法：`build_index` 整体包进 `_HOT_LOCK`（RLock，`hot_refresh` 里再调进来不死锁）。

**这条的守护测试我写错了两次**。第一版数 `_index_build_one` 的并发峰值——删掉锁照样绿，因为 `hot_refresh` 走的是 `_ix_refresh_subtree`，根本不碰 staging，两条路径在测试里压根没重叠。第二版改成直接量锁的效果：另一个线程持有 `_HOT_LOCK` 0.35 秒，主线程计时调 `build_index`，断言等待时间 > 0.2 秒。这次删锁会红。

### 2.5 攻击五（真机才暴露）：`_ix_refresh_dir` 每刷一个目录都全表扫

**攻击**：你说热目录刷新是 300 毫秒级。那 216 个目录、82 万行的库呢？

真机实测 `E:\下载`（216 目录 / 2,741 文件）刷新 **8,409 ms**。第一次搜索因此花了 8,914 ms。

根因：`_ix_refresh_dir` 删旧块写的是 `DELETE FROM files WHERE dir_id = ?`，而 `files` 表**故意没有 `dir_id` 索引**——建表设计就是一个目录的文件连续插入、`dirs.f0/n` 记着这段 rowid 区间。于是每次删除都退化成全表扫：216 × 827,319 ≈ **1.8 亿次行比较**。

修法：删旧块改走 `dirs.f0/n` 记的 rowid 区间。真机重测 **8,585 ms → 768 ms**。

**这条最值得记的教训是：性能缺陷只会在真实数据规模上暴露。** 临时目录里建几十个文件的库，两种写法都是毫秒级，测试永远是绿的。

### 2.6 攻击六：搜得到已经删掉的文件

**攻击**：索引是快照，磁盘会变。快照里指向已删除文件的条目，会被原样返回给用户吗？

真机探针：往 `D:\下载` 写文件 → 搜到 → 删掉 → 再搜，**仍然返回 1 条**。

根因：`_ix_top_one`（问「什么最占空间」）在 1.42.0 就加了 `os.path.exists` 过滤，`_ix_query_one`（按名字搜）没有。两个入口读同一份快照，一个校验一个不校验。

修法：`_ix_query_one` 加同样的存活过滤，并且和 `_ix_top_one` 一样**多取一倍再截断**——只取 `limit` 条再过滤的话，前排有几个失效就会少给答案。代价是每次搜索多 20 毫秒左右（`pdf` 99 ms / `setup` 154 ms / 搜不存在的名字 145 ms）。

### 2.7 攻击七：失败的边界条件

- **盘拔了 / 网络盘断开**：根不存在，不是「过期」是「离线」，直接跳过，不重建。
- **索引超配额**：`index_max_mb` 默认 2048，`<= 0` 视为不限制。超限时保鲜只 `skipped`，不动。
- **`index_max_mb` 存进负数**：`index_quota_ok()` 拿它当分母，永远返回超限，索引从此再也不刷新，而用户看到的只是「怎么老是旧数据」。所以设置校验下界是 0 而不是 1。
- **一次改了几千个目录**：`_IX_TOUCH_MAX_DIRS = 4000` 以上整批放弃，等下次重建。注意数的是**目录总数**不是**库的个数**——`plan` 按库 id 分键，一台机器通常只有一两个库，拿 `len(plan)` 当判断条件永远不会触发（这是我自己第一版写错的地方）。
- **写穿出错**：全部 `except Exception: continue` 吞掉。写穿是优化，不是业务的一部分；它出错绝不能连带让用户的整理操作失败。那种取舍是拿数据正确性换缓存新鲜度，方向反了。

### 2.8 攻击八：「旧数据」本身是不是问题

**攻击**：你允许数据旧 10 分钟，那用户问「现在 C 盘还剩多少」你答的是十分钟前的账，这不算错答吗？

**结果**：这不算错答，但**不说出来就是错答**。类比 CDN 的 `Cache-Control: max-age` 和 DNS 的 TTL——旧是允许的，前提是标出来。

修法：每个 `search.top` / `search.folders` 返回都带 `age_sec` / `age_text` / `stale`，提示词明写「这是账本的时间，不是文件的修改时间；用户问『现在』时必须说出来，没有这个字段就不要自己编一个时间」。

## 三、修正后的最终方案

### 3.1 结构

```
写操作 ──→ Tier 0 写穿 ──── 成本 0，立即生效
                              apply / undo / trash_delete / hard_delete / clean_cache_paths

查询 ──→ 命中 → 直接返回（带 data_age）
     └→ 未命中 → Tier 1' 局部刷新（≤ 300ms 预算，仅限已索引范围之内）
                    └→ 仍无 → 真的没有

后台 ──→ Tier 3 抽样校验（每 30 秒醒一次，热目录按档位重扫、全库 6 小时抽查一次）
                    └→ 判过期才重建
```

关键点：**Tier 1'（原来的文件监听）和 Tier 2（USN 日志）都被实测否决，由 Tier 3 的「便宜重建」整体吸收。**

### 3.2 数据格式（schema 3）

`dirs` 表反规范化：

```sql
CREATE TABLE dirs(
  id INTEGER PRIMARY KEY,
  path TEXT,
  mtime REAL,          -- 该目录自身的 mtime，用于浅层变更检测
  scanned_at REAL,     -- 这一行是什么时候写的
  fresh INTEGER,       -- 历史遗留列（schema 2 起恒为 1、无人读取），等下次升级删
  f0 INTEGER,          -- 本目录文件行的 rowid 起点
  n INTEGER,           -- 本目录文件行的条数
  size_sum INTEGER NOT NULL DEFAULT 0,
  n_files INTEGER NOT NULL DEFAULT 0
)
```

**为什么反规范化而不是建索引**——四个实测数字决定的：

| 方案 | 目录聚合耗时 |
|---|---|
| 无索引（`JOIN` + `GROUP BY`） | 671 ms |
| 只有 `files(size)` | 638.6 ms |
| 只有 `files(dir_id, size)` | 695.9 ms |
| 两个索引都有 | 654.7 ms |
| **反规范化 `dirs.size_sum`** | **32.5 ms** |

任何 `files` 上的索引都对聚合无效，因为聚合必须扫完 `files` 每一行。反规范化是唯一有效的方向，代价是库体积 +9.3 MB、单目录增量维护 0.2 ms。

**同样刻意不建 `files(size)` 索引**：按体积取前 20 条，无索引 92.2 ms、建索引要 889.9 ms、建完 0.1 ms。92 毫秒已经在「1 秒内」的验收线之下，建索引纯属过早优化。

`_ix_folders_one` 里有一句 `WHERE n_files > 0` 必须留着——`JOIN files` 天然排除空目录，直接查 `dirs` 会把空目录也带出来，让「下钻某个目录」的结果里多一行体积为 0 的它自己。**这是纯性能重构改动了一处隐蔽语义，只有测试能发现。**

### 3.3 实测验收

真机（D:\ 595,754 文件 / E:\ 827,319 文件，共 141 万，引擎为 1.42.3）：

| 项目 | 结果 |
|---|---|
| 问「什么最占空间」 | **284 ms**（三次 284 / 284 / 272 ms） |
| 答案含已删文件 | **0 条**（`search.top` 200 条逐条 stat；按名字搜三组各 20 条） |
| 热目录刷新 | 首次搜索 **1,244 ms**（其中刷新本身 768 ms：`D:\下载` 84 ms、`E:\下载` 888 ms） |
| 第二次同一搜索 | 144 ms（命中索引，不补扫） |
| 删掉文件后立刻搜 | 150 ms / 命中 0 条 |
| schema 2 → 3 自动升级 | **7.9 秒**，用户零操作 |
| 索引库实际状态 | 两个库 `user_version=3`，`dirs` 含 `scanned_at / size_sum / n_files`；D 141.3 GB、E 256.3 GB |
| 新下载文件不重建索引即可搜到 | 通过（`D:\下载` 写入 → 1,244 ms 后命中 1 条） |
| 设置页三开关可存可读 | 通过（`check` / `2048` / `True`） |

热目录候选的识别也对了：`_hot_roots()` 现在返回 `['D:\\下载', 'E:\\下载']`，不再是五个从没索引过的 C 盘用户目录。

### 3.4 可控性

设置页三个开关，不是「一个新鲜度开关」：

- **索引新鲜度**：实时（每分钟扫一次热目录）/ 按需（每 10 分钟，默认）/ 只手动（不自动扫盘）
- **磁盘占用上限**：默认 2048 MB，填 0 不限制
- **后台重建**：空闲时校验并重建（默认开）

用户原话是「最好可以可控不然扫磁盘次数多会伤磁盘」。给三档而不是一个开关，是因为「可控」的实际含义是**我能决定什么时候被打扰**，而不同人对打扰的容忍度差别很大。

### 3.5 这版仍然没做（有理由的）

| 没做的 | 为什么 |
|---|---|
| `ReadDirectoryChangesW` 文件监听 | 热目录全量重建只要 300 ms，监听器换来的只是这个窗口期，代价是常驻句柄 + 白名单维护 + 漏事件的静默不一致 |
| USN 日志增量 | 需要管理员权限，软件定位是「装给朋友用」，不能假设权限 |
| `files(dir_id)` / `files(size)` 索引 | 实测对目标查询全部无效或收益远小于建索引成本 |
| `dirs.fresh` 死列 | 是历史遗留，但删列要改 schema，等下一次升级一并处理，不值得为它单独升一次版本 |
| `src/archive/util.rs` 5 个 never-used 函数 | 编译期 12 个 dead-code 警告，纯清理，与本次目标无关 |

### 3.6 这套设计的失败边界

诚实说明它什么时候不管用：

- **索引范围完全不含用户实际下载的位置**（比如只索引了 `D:\工作`，文件下到 `E:\下载`）→ 保鲜管不到，因为**保鲜绝不扩大索引范围**。这种情况需要提示用户去搜索页添加目录，而不是偷偷替他加。
- **单目录内文件数十万**（比如一个目录里堆了 30 万个文件）→ 刷新那个目录本身就要秒级。目前的做法是超过 `_HOT_INLINE_MAX = 30000` 就跳过热目录内联刷新，交给后台。
- **用户在软件外大量增删文件后立刻提问** → 若恰好超出热目录范围，会看到旧数据。这是 `data_age` 存在的理由。

## 附：这一轮最贵的一条经验

这一轮写的新测试里，**有五条第一次是绿的但根本没测到东西**：

1. `hot_refresh` 并发（RPC 环单线程，天然串行，构造不出并发）
2. `index_touch` 规模守卫（子进程与进程内 `cache_dir` 不同，`plan` 是空的）
3. `build_index` 与 `hot_refresh` 不重叠（两条路径在测试里压根没重叠）
4. 旧格式库判过期（后来才发现，原本被 `except` 吞掉）
5. 刷目录不扫全表（被刷目录本身就是全库，两种写法碰的行数一样多）

它们变绿的原因各不相同，共同点是：**测试构造的数据规模或路径，恰好让缺陷显露不出来。**

判断办法始终只有一条——**把修复改回缺陷版，看它变不变红**。测试变绿不代表它测到了东西。

这也是为什么 `build.ps1` 的测试门禁值得在最开始就做：它把「跑不跑测试」从人的自觉变成了构建的前置条件。门禁第一次跑就抓到了一处纯性能重构改坏的隐蔽语义（`WHERE n_files > 0`）。
