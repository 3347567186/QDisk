# 版本管理与发布规范（硬性规定）

本文件是项目的强制规则，任何会话、任何人都必须遵守。与本文冲突的做法一律视为错误。

## 0 版本线基线

**2026-11-15 起，版本线从 `1.0.0` 重新开始。** 此前的 `2.0.0` / `2.1.x` 是旧编号，产物已全部删除、不再参与任何判断；
回滚只回滚到本版本线内的上一版。`1.0.0` = 单一源码树 `D:\Tools\TidyAssistant`（Tauri 外壳 + Python 引擎）的第一个正式版本。

## 1 每次改动都必须有版本号

- **只要动了代码（Rust / 前端 / 引擎）或打包配置，就必须递增版本号**，不许出现「改了代码但版本号没变」的情况。
- 纯文档、注释、README 的修改也必须递增，按 `patch` 处理，保证「文档对得上版本」。
- 版本号只有两个权威来源，且必须一致：
  - `src\src-tauri\tauri.conf.json` 的 `version`
  - `src\src-tauri\Cargo.toml` 的 `[package] version`
- 不要手改这两个字段。用脚本递增，它会同时写入两处并从同一个值生成产物名：

```powershell
.\build.ps1 -Bump patch    # 1.0.0 → 1.0.1
.\build.ps1 -Bump minor    # 1.0.1 → 1.1.0
.\build.ps1 -Bump major    # 1.1.0 → 2.0.0
```

## 2 按修改程度选版本位

| 位 | 何时用 | 例子 |
|---|---|---|
| `major` | 架构换代、数据格式不兼容、需要用户重新学习怎么用 | pywebview → Tauri 外壳；规则文件格式改版导致旧配置无法直接读 |
| `minor` | 新增功能、新增页面、新增可配置项，且向后兼容 | 新增「按修改时间分类」策略；新增日志页筛选；新增托盘菜单项 |
| `patch` | 修复 bug、性能优化、无行为变化的内部重构、文档更新 | 修卸载页空表格；引擎调用改 async；目录重组 |

判断口径：**看用户的感受，不看代码行数**。用户能感知到「多了东西」→ minor；只是「原来不对的现在对了」→ patch；「整个东西变了」→ major。

一次提交同时包含多种改动时，按**最高等级**的那一项定版本。

## 3 只保留最新版和上一版

`release\` 里最多保留两个版本，各类型各两份：

```
release\
├── TidyAssistant_1.0.1_x64-setup.exe      ← 最新
├── 整理助手_1.0.1_便携版.zip               ← 最新
├── TidyAssistant_1.0.0_x64-setup.exe      ← 上一版（留作回滚）
└── 整理助手_1.0.0_便携版.zip               ← 上一版
```

- 规则由 `build.ps1` 自动执行：每次 `-Bundle` / `-Portable` 之后按版本号排序，删除第三旧及更早的同类产物，**不要手工往 release 里堆历史包**。
- 要长期归档的版本放 `release\archive\`（不参与清理），由负责人决定，不属于日常流程。
- 回滚 = 直接装上一版安装包；数据目录 `%LOCALAPPDATA%\整理助手数据` 不变，配置向后兼容由 `migrate_engine.py` 负责。

## 4 发布流程

1. 确认改动已自测，写清「改了什么、影响谁」。
2. `docs\01-当前版\变更记录.md` 顶部追加一条：版本号、日期、改动要点、已知问题。
3. 递增版本并打包：

   ```powershell
   cd D:\Tools\TidyAssistant
   .\build.ps1 -Bump patch -Bundle -Portable
   ```

4. 按 `docs\01-当前版\打包与发布.md` 第 6 节验收清单逐条过一遍。
5. 交付时说清版本号与产物路径；版本号没变就说明这次没有实际改动。

## 5 禁止事项

- 禁止「先发布、后补版本号」。
- 禁止同一版本号对应两份不同的二进制（会导致回滚时无法判断装的是哪个）。
- 禁止在 `release\` 里保留第三旧及更早的包，也禁止把中间产物（`D:\Builds\` 里的 exe）直接当交付物。
- 禁止改动后不重新构建就宣称「已更新」——用户跑的是 `tidy-assistant.exe`，不是你的源码。
