# AI 操作能力与安全边界

状态：**已实现**（1.28.0）。查询侧架构见 [AI助手方案](./AI助手方案.md)；
本文只讲「让 AI 动手」这一层：能做什么、经由什么路径、被什么拦住、出了问题怎么回退。

---

## 一、一句话

模型能**提议**任何一件软件本身会做的事，但没有一条路径能让它**直接**改动文件。
每一次真正的改动都走同一条流水线：

```
模型选动作 + 参数 → 引擎 dry-run 出预览 → 落成提案（10 分钟 / 一次性 / 参数哈希）
   → UI 卡片（人看：几项、多大、哪些被拒、撤不撤得回）
   → 人点执行 → 再过一遍路径闸与预算闸 → 引擎真跑 → 写审计 → 给「撤销」按钮
```

任何一环缺失，动作都不会发生。默认档位是「关闭」，此时工具表里连 `propose_action` 都不发，
助手行为与 1.27.x 完全一致。

---

## 二、为什么不做「31 个方法 1:1 映射」

引擎有 31 个 `_ENGINE_METHODS`，最直接的实现是给每个方法套一个工具。这条路走不通，原因有三：

1. **工具数塌陷**：工具表一过二十，模型选错工具的比例会明显上升（见文末参考）。
   再加十几个写工具，查询准确率会跟着一起掉。
2. **参数不是平的**：`organize` 有 6 个参数、`migrate.apply` 有 6 个、`apps.uninstall` 有 3 种 mode。
   让模型逐字填对这些参数，比让它选对一个动作难得多。
3. **没法统一加闸**：31 个入口就有 31 处要检查路径、预算、确认、审计。漏一处就是破口。

所以改成**单入口 + 目录**：

- 模型只看到一个 `propose_action(action, args)`，配一份随版本固定的【动作目录】文本；
- 每个动作的 schema、预演、执行、撤销、风险，全部写在 `registry.js` 的一张表里；
- 闸门只在提案层做一次，不管底下是哪个引擎方法。

模型侧因此只多了一个入口，而不是十九个。

## 三、三层结构

| 层 | 文件 | 职责 | 谁能调 |
|---|---|---|---|
| 路径闸 | `ai\guard.js` | 纯函数：一个路径能不能被 AI 碰 | 其它两层都调 |
| 动作层 | `ai\registry.js` | 19 个动作的 schema / 预演 / 执行 / 撤销 | 提案层 |
| 提案层 | `ai\proposals.js` | 权限、预算、TTL、卡片、执行、审计、撤销 | UI（**不是模型**） |
| 工具层 | `ai\tools.js` | 把 `propose_action` 等 19 个工具暴露给模型 | 模型 |

关键点：**`commit` 不在工具层**。模型能调到的写入口只有 `propose_action`、
`list_proposals`、`cancel_proposal`，三个都不改文件。

## 四、模型看到的工具面

| 组 | 工具 |
|---|---|
| 只读（原 11 个） | `list_dir` `read_file` `open_path` `disk_roots` `top_files` `empty_dirs` `file_signals` `installed_apps` `search_files` `organize_preview` `last_organize` |
| 只读（新增 5 个） | `archive_entries` 看压缩包内清单 · `clean_candidates` 列可清缓存/截图 · `settings_read` 读可改设置的当前值 · `search_roots` 看索引状态 · `navigate` 跳到某个页面 |
| 提案（3 个） | `propose_action` 提议 · `list_proposals` 看自己提过什么 · `cancel_proposal` 撤回提案 |

工具总数从 11 涨到 19，但**写入口仍然只有一个**，所以选择难度增加有限。
`navigate` 有副作用（换页），但它不改文件，且不受权限档位限制。

## 五、19 个动作

「风险」决定自动执行的边界，见 §六。可撤销的意思是「有按钮能把这次改动退回去」。

| # | 动作 | 中文 | 类 | 风险 | 撤销方式 |
|---|---|---|---|---|---|
| 1 | `organize.apply` | 按类型整理 | 整理 | 1 | 引擎 `undo` 逐个目录回退 |
| 2 | `files.delete` | 删除 | 文件 | 2（回收站）/ **3（永久）** | 回收站：打开回收站；永久：无 |
| 3 | `files.remove_empty` | 删空文件夹 | 文件 | 2 | 无 |
| 4 | `archive.extract` | 解压 | 压缩包 | 1 | 把新建出来的目录移进回收站 |
| 5 | `archive.create` | 压缩 | 压缩包 | 1 | 把新建的包移进回收站 |
| 6 | `clean.cache` | 清缓存 | 清理 | **3** | 无（缓存是重生成的东西，删了就是删了） |
| 7 | `clean.shots` | 清截图 | 清理 | 2 | 打开回收站 |
| 8 | `apps.uninstall` | 卸载 | 程序 | **3** | 无（走的是程序自己的卸载器） |
| 9 | `apps.delete_entry` | 删注册表项 | 程序 | 2 | 无 |
| 10 | `apps.force_remove` | 强制删除 | 程序 | **3** | 无 |
| 11 | `apps.cleanup` | 清残留 | 程序 | **3** | 无（会先导出 `.reg` 备份） |
| 12 | `apps.remove_store` | 移除商店应用 | 程序 | **3** | 无 |
| 13 | `search.rebuild` | 重建索引 | 索引 | 1 | 无（重建即可） |
| 14 | `rules.run` | 按规则整理 | 整理 | 2 | 无 |
| 15 | `migrate.run` | 迁移目录 | 文件 | **3** | 仅复制模式算可逆；移动无 |
| 16 | `settings.set` | 改设置 | 设置 | 1 | 写回旧值 |
| 17 | `autostart.set` | 开机启动 | 设置 | 1 | 写回旧值 |
| 18 | `schedule.set` | 计划任务 | 设置 | 1 | 写回旧值 |
| 19 | `logs.clear` | 清日志 | 清理 | 2 | 无 |

风险 1 / 2 / 3 的含义：

- **1 = 可逆的轻操作**：能完整退回，代价只是重做一次。
- **2 = 有代价**：进回收站、删注册表项、删空目录。多数捞得回来，但要说清楚。
- **3 = 不可逆**：永久删除、卸载、强制删除、清缓存、迁移。卡片上会明说「撤不回来」。

`files.delete` 是同一个动作两种命运：`mode: 'trash'` 是风险 2、可撤销；
`mode: 'permanent'` 是风险 3、**任何档位都要输入确认词**。这个区分由动作自己按参数报
（`plan()` 返回 `riskNow` / `reversibleNow`），不是写死在表里的静态值。

## 六、四档权限

设置页「AI 助手 → 允许 AI 动手」与对话底栏都能改，改完立刻生效（对话页刷新后同步底栏）。
默认 **关闭**。

| 档位 | 自动执行什么 | 说明 |
|---|---|---|
| 关闭 | 什么都不 | 只读。`propose_action` 不进工具表，模型连提议都做不到 |
| 逐次确认 | 什么都不自动 | 每个动作都变成卡片，点了「执行」才动 |
| 自动 | 风险 1 且可撤销 | 整理、解压、压缩、索引、设置这类跑完给 3 秒「停止」 |
| 放手 | 风险 ≤2 **且可撤销**（或风险 1） | 连删到回收站也自动；**撤不回来的仍然要人点** |

放手的边界是刻意写的：`risk<=2 && (可逆 || risk<=1)`。
少了这个「可逆」条件，删空文件夹、删注册表项、清日志在放手档就会自动执行——
它们都撤不回来，不该有人不在场的时候发生。

自动执行时卡片仍会出现，带 3 秒倒计时和「停止」；点停止等于拒绝。

另有 **7 类开关**（整理 / 文件 / 压缩包 / 清理 / 程序 / 索引 / 设置），
可以只放开「整理」而锁死「清理」。关掉的类别，模型提议时会直接收到拒绝理由。

## 七、路径闸（`guard.js`）

所有动作在预演前先把路径过一遍 `AIGuard.denyWhy()`。规则是**白名单式拒绝**：
能明确判定为危险的，一律拒绝并给出原因；判断不了的不猜。

| 类别 | 拦什么 |
|---|---|
| 路径形态 | UNC（`\\server\share`）、`\\?\` 设备路径、相对路径、含 `..` 的越界路径 |
| 卷与系统 | 盘符根、`\Windows`、`\Program Files`、`\Program Files (x86)`、`\ProgramData`、`\$Recycle.Bin`、`\System Volume Information`、`\Recovery`、`\Boot`、`\PerfLogs` |
| 自身 | 程序目录（exe 所在目录整棵）、数据目录（只放行 `数据\cache`；`数据\ai` 永远拦） |
| 主目录 | 主目录本身，以及桌面 / 文档 / 下载 / 图片 / 视频 / 音乐 / OneDrive 这几个目录**本身**（其下的具体文件不拦） |
| 启动项 | 用户与公共启动目录 |
| 敏感目录 | 路径里出现 `.git` `.ssh` `.gnupg` `.aws` `.kube` `.docker` `.azure` 段 |
| 系统文件 | `pagefile.sys` `hiberfil.sys` `swapfile.sys` `bootmgr` `ntldr` `boot.ini` `ntuser.dat` 等 |

`check(list)` 是整批语义：里面有一项不过，整批不过，并返回 `{path, why}`。
不做「跳过坏的、执行好的」——部分执行最容易留下说不清的状态。

注意这一层是**第二道**闸，不是第一道：引擎自己也有
`_files_delete_guard_why` / `cache_path_forbidden` / `empty_dir_denied` 等保护。
两层都过才动。

## 八、预演闸

`propose_action` 内部先调引擎的 dry-run，把「会发生什么」问清楚再落提案：

| 动作 | 预演从哪来 |
|---|---|
| 整理 / 规则整理 | `scan`（`confirm:false`）给的 `plans` |
| 删除 | `files.delete` 的 `confirm:false` 分支（1.28.0 已扩成带 `items` / `failed` / `total_size` / `count`） |
| 清缓存 / 清截图 | `cache.list` / `shots.scan` |
| 迁移 | `migrate.plan` |
| 卸载 / 强制删除 / 清残留 | 对应方法的 `confirm:false` |
| 设置 / 开机启动 / 计划任务 | 先读旧值，卡片上同时写旧值与新值 |

预演里出现「被引擎拒绝的项」时，**提案直接失败**，不静默改成部分执行。
理由同上：用户看到「删 12 项」就该是 12 项，不能点下去变成 9 项。

目录体积用 `_tree_size(p, 20000)` 限 2 万文件，超了标 `partial: true`——
预演不能把单线程引擎卡住。

### 八·补、批量确认（一张卡里挑着执行）

一张卡默认是「整批照做」，但多数时候用户只想做其中几条。1.30.0 起：

- 动作的参数里只要有「能放多条路径」的列（`paths` 之类），卡片上就多一列复选框，
  **默认全选**，可以逐条勾掉，也可以「全选 / 清空」。
- 勾选一变就调 `proposals.preview()` 用同一套 dry-run 重新算：卡片上「N 项 / 多大」
  跟着真实数字走，不拿整批去按比例拆分。选中 0 项时执行按钮直接禁用。
- 执行时 `commit(id, { approvedBy:'user', paths:[...] })` 只接受**原提案里真实存在的子集**；
  混进一条新路径当场拒绝（`勾选的项不在原来的提案里，已拒绝执行`）。
- 子集在执行前会**再预演一次**，并按子集重新校验单次项目数与字节数上限——
  勾一半不能靠整批的数字蒙过预算。
- 勾选数会写进审计那行的 `result`（`已把 1 项移入回收站（勾选 1 项）`），事后能看出当时只挑了部分。
- 有勾选框的卡**不进自动倒计时**：用户正在挑东西，倒计时会把挑到一半的东西执行掉。

## 九、预算与熔断

| 项 | 默认 | 上限 |
|---|---|---|
| 每轮最多提案 | 2 | 10 |
| 每会话最多执行 | 30 | 200 |
| 单次最多项目 | 200 | 20000（整理类放行到 2 万） |
| 单次最多字节 | 4 GB | 20 GB |
| 同时挂着的提案 | 3 | — |
| 提案有效期 | 10 分钟 | — |

超限的回复是「这一轮已经提了 N 次，到上限了」「还有 3 个提案等用户处理」这类可自纠的话，
模型能看懂并改用别的方式，而不是把错误堆栈丢给用户。

熔断：同一个 `action + 参数哈希` 连续被拒 2 次，之后直接拒绝并不再弹卡片。
这防的是「模型换个说法反复提同一件事」把确认疲劳刷满。

## 十、审计

每次提议 / 批准 / 拒绝 / 过期 / 执行 / 结果 / 撤销都落一行：

```
%LOCALAPPDATA%\整理助手数据\ai\journal-YYYYMM.jsonl
```

```json
{"n":42,"at":"2026-11-18T18:20:11.482Z","phase":"commit","id":"p1x9k3","action":"files.delete",
 "cat":"files","items":12,"bytes":3006477107,"hash":"a1b2c3d4","result":"ok","why":"","p":"9f2c","h":"7d1e"}
```

- `n` 是行号，`hash` 是这次参数的摘要，`p` 是上一行的 `h`，`h` 是「上一行摘要 + 本行内容」的摘要。
- 这是**防误改**，不是防篡改：djb2 不是密码学哈希，声明清楚比假装安全更有用。
- 按月份分文件（`journal-202611.jsonl`），不自动清理——用户想看「它到底动过什么」时，
  这份日志是唯一凭据。

## 十一、撤销

执行成功的卡片会多出一个「撤销」按钮，按 `undoKind` 分派：

| undoKind | 怎么做 |
|---|---|
| `undo` | 调引擎 `undo`，逐个整理目录回退 |
| `recycle` | 打开回收站（东西在里面，让用户自己挑） |
| `trash-path` / `trash-file` | 把这次新建出来的东西移进回收站（仅当它原本不存在） |
| `setting` / `autostart` / `schedule` | 写回旧值 |
| `none` | 没有撤销按钮，卡片上在动手前就写明「撤不回来」 |

「撤不回来」必须在**动手前**说，不是在撤销失败后说。

---

## 十二、绝对禁止

这些不在动作目录里，模型连提议都提不出来；即使它编一个动作名，`registry.get()` 也返回空：

- 跑任意命令 / 脚本（没有 `exec` 类动作，永远不会有）
- 改 AI 自己的端点、密钥、权限档位、预算上限（否则边界可被自己解开）
- 改程序自身目录、改数据目录（`数据\cache` 除外）
- 改网络路径 / UNC 路径
- 改注册表中除「卸载项」以外的键
- 无人值守地定时整理（计划任务可以由用户自己建，AI 只能提议一次）

| 位置 | 内容 |
|---|---|
| `app.json` → `ai_ui.agent` | 档位、七类开关、四个预算值 |
| `数据\ai\journal-YYYYMM.jsonl` | 审计 |
| `数据\ai\s-<id>.json` | 会话（含提案卡片的重放信息） |

## 十五、已知限制

1. **一次一件**：一轮对话最多 2 个提案，超了要用户先说一句「继续」。这是为了让人真的看见每一件。
2. **预演不是原子的**：预演与执行之间文件可能变（用户自己删了、别的程序占了）。
   执行时引擎会重新校验并把这些项记进 `failed`，不会因为一项失败就回滚全部。
3. **不能跨动作编排**：「先整理再压缩再删源」需要三次提议、三次确认。故意如此。
4. **抽屉里的对话是另一份会话**：它的提案计数与主对话页分开，两边都从同一份档位读。
5. **动作目录随版本走**：`AIPrompt.setCatalog()` 灌进去的目录文本在同一个版本内固定，
   保证 system prompt 前缀字节不变、KV cache 不失效。
6. **系统盘按用户主目录所在盘推断**：Windows 装在非 C 盘时，`guard.js` 的系统目录判断会偏，
   此时以引擎自己的闸门为准（两层都过才动，偏的一面只会更严或漏给引擎兜）。
