# 本地数据「只留最新版」——第一性原理与红队审查

版本：1.42.4　・　对应变更记录同版本条目

---

## 一、第一性原理重推

### 抛开现有做法，先看基本事实

| 事实 | 数字 |
|---|---|
| 数据目录总大小 | 126.75 MB |
| 其中索引库 | 101.9 MB（D 盘 595,754 文件 + E 盘 827,319 文件） |
| 其中 WebView2 旧目录 | 11.17 MB（孤儿，无代码引用） |
| 其中历史 / 日志 / 缩略图 | 合计不到 0.4 MB |
| 索引库是否存在备份 | **不存在**。`写 .new → os.replace 原子替换`，成功路径无第二份 |
| 索引库是否有可回收空洞 | **没有**。`freelist_count` 0 和 1，合计 4 KB；`VACUUM` 全项目零出现 |

结论：**「索引库留了两份」这个症状不存在**。用户说「体积爆炸」，但当下真正占地方的 101.9 MB 是 141 万文件的真实数据——那是索引在干活，不是冗余。

### 那用户真正想解决的是什么

不是「索引瘦身」，是**「我的软件不会在我看不见的地方一直变大」**。

这是一个信任问题，不是一个磁盘问题。当前 126 MB 完全无害。用户担心的是趋势：今天 126 MB，一年后会不会 6 GB？他没法验证，因为**没有任何机制给他一个上限**。

所以真正的目标是：**把每一个会一直变大的地方，都钉一个明确的上限，并且这个上限是可解释的。**

### 从这个目标推导分类

判断一个落点该怎么处理，只需要问两个问题：

1. **是软件自己攒的，还是用户的数据？**
2. **删掉之后，用户会失去什么？**

| 落点 | 谁攒的 | 删掉会失去什么 | 结论 |
|---|---|---|---|
| 整理历史 | 软件 | 更早那些整理的撤销能力 | 留最近 N 份 |
| 运行日志 | 软件 | 没有（排障用的） | 留最近 N 份 |
| 缩略图 | 软件 | 没有（重新生成） | 按体积封顶 |
| 卸载备份 | 软件 | 更早程序的回滚凭据 | 留最近 N 份 |
| 覆盖时的 `.bak` | 软件 | 更早那版的旧文件 | 每个原文件留 1 份 |
| WebView2 旧目录 | **不是软件攒的**（历史手工改名残留） | 万一正主不在，就是唯一一份书签与登录态 | **正主在才删** |
| 索引库 | 软件 | 重建要 5 秒 | **不删**——它不是垃圾，是缓存，且已有原子替换 |
| 用户整理过的文件 | **用户** | 全部 | **永不主动删** |

最后两行是这份设计的边界：**缓存可以重建，用户数据不能。** 任何「看起来很大所以清掉」的判断，都必须先过这一关。

### 被这个推导否决的方案

- **「按天保留」**：同样「留 30 天」，一天整理两百次的用户和三个月整理一次的用户，体积差两个数量级。按天不是上限，是概率。
- **「给索引加 `VACUUM`」**：实测没有空洞可收，加了只是每次重建多花几秒。
- **「索引只保留最新版」**（用户原话的字面意思）：已经是这样了，做了等于没做。真正需要改的是别处。
- **「加一个『立即清理』大按钮」**：用户要的是「不再长」，不是「再给他一个需要记得按的按钮」。清理必须是自动的，按钮只能用来预演。

## 二、红队审查：8 条攻击

站到最强反对者的位置，找这套方案会在哪儿断。

### 攻击 1：按 mtime 排序，mtime 可靠吗？

**不可靠。** 从备份还原、从别的机器拷过来，mtime 都会被改。

**影响**：可能把「内容最旧但 mtime 最新」的那份留下，删掉真正最新的。

**缓解**：这些目录里的东西是我们自己写的，正常路径下 mtime 可信；异常路径下最坏结果是「留错了哪一份」，而所有这些文件都是可重建或可接受的损失。**接受这个边界**，不为此引入哈希或序号命名的复杂度。

### 攻击 2：`pending` 保护依赖 `journal.db` 能读，读不出来呢？

`_mig_job_busy` 读不出来就返回 False = 判定「不忙」= 允许删。

**但**：`journal.db` 读不出来意味着这个任务的续跑信息已经没了，它**本来就无法续跑**。删掉一个无法续跑的任务目录，不是数据丢失，是清理死数据。

**这里有个真实教训**：第一版这个函数因为缺 `import sqlite3`，`NameError` 被 `except Exception` 吞掉，**恒返回 False**——等于保护完全失效，正在跑的任务照样被删。测试抓出来了。它说明一件事：**兜底的 `except` 会把「读不懂」和「没问题」压成同一个返回值**，而这种沉默正是最危险的。

### 攻击 3：`webview\` 存在，就等于它在用吗？

不一定。可能是上次崩溃留下的空目录。

**影响**：误删真正的 WebView 数据。

**缓解**：这条判断的方向是**保守**的——`webview\` 不存在时**不删**。所以误判只会发生在「正主存在但没用」，而这个场景下正主里也有可用的 WebView 数据（同一份配置）。**接受。**

### 攻击 4：`.bak` 只留 1 份，会不会把用户刚被覆盖的文件删掉？

**这是第一版真实存在的 bug。** 判据写成「除了传入的那个路径之外都删」，而 `resolve_dst` 传入的是**原文件路径**，于是刚生成的 `.bak` 也被当成旧副本删掉——用户选了「覆盖」，结果原文件和新备份一起没了。

**已修**：判据改成「这组 `.bak` 里按 mtime 最新那份留下」。测试断言 `报告.bak-20260103120000.txt` 必须还在。

### 攻击 5：清理跑在 `apply()` 里，会不会拖慢整理？

`apply()` 末尾调 `prune_maybe()`，节流到每小时一次。真跑时是几个目录的 `scandir`，文件数在几十到几百量级，**毫秒级**。

**但**：如果用户历史里有 10 万条（一次性整理过几十万个文件），第一次运行会删很多。**缓解**：逐个 `os.remove`，失败跳过，不阻塞；且这是首次一次性成本。

### 攻击 6：后台线程和 `apply()` 同时跑，会撞吗？

会。两边都可能删同一批文件。

**影响**：一个删掉了、另一个 `os.remove` 报 `OSError`。

**处理**：`except OSError: continue`。**这是刻意不做锁的**——为两个都在做「删旧文件」的动作加一把锁，成本高于收益。最坏结果是少删了几个，下次再删。

### 攻击 7：删掉历史，用户还能撤销吗？

`undo()` 按 `folder` 找**最近一条**历史。所以：
- 同一个文件夹整理多次 → 只需要最近一条 → 留 50 份绰绰有余
- 不同文件夹各一条 → 50 个文件夹的撤销能力

**边界**：整理了 51 个以上文件夹后，最早那个的撤销能力消失。**这是明确的取舍**，写进设置页的数字框里让用户自己调（0–10000）。

### 攻击 8：这个方案本身，是不是在解决一个不存在的问题？

这是最强的一条。

**当下 126.75 MB，清完只剩能省 11.17 MB。** 用户担心的「体积爆炸」，现在没有发生。

**承认这一点。** 这一版的价值不在「省了 11 MB」，而在：
1. 六处无上限增长点现在都有上限了；
2. `log_keep_days` 这个存了几个月没人用的死设置，现在真的生效了；
3. 11.17 MB 的孤儿目录会被自动收掉（这是唯一当下可见的收益）。

**如果一年后这些目录长到 2 GB，这一版就是那次没爆的原因。** 但它现在确实不紧急——所以做的是「关水龙头」，不是「倒掉一浴缸水」。

## 三、修正后最终方案

### 结构

```
触发（三个，全部节流到每小时一次）
  ├─ apply() 末尾        → 整理后立刻收
  ├─ 引擎启动后台线程     → 从不整理的用户也受益
  └─ prune.run {dry_run} → 设置页「先看能清多少」，只报不删
        ↓
prune_data_dir()
  ├─ history     留 50 份（mtime 排序）
  ├─ logs        留 min(log_keep_days, 60) 份
  ├─ backup      留 3 份（目录粒度）
  ├─ migrate     留 5 份，pending 一律不碰
  ├─ thumbs      256 MB 封顶，超了从最旧删
  └─ webview_bak 正主在才删
        ↓
失败一律跳过，不抛错（清理是维护动作，不能连带让整理失败）
```

### 三处刻意不做的事

| 不做 | 为什么 |
|---|---|
| 不进回收站 | 这些是软件自己攒的临时数据，进回收站只是换个地方继续占空间 |
| 不给 `.bak` 加锁 | 两个清理者撞车，最坏是少删几个 |
| 不按天保留 | 按天不是上限，是概率 |

### 边界条件清单

| 条件 | 行为 |
|---|---|
| 用户把 `prune_enabled` 关掉 | 整个函数什么都不做，返回 `note` 说明已关闭 |
| `prune_history_keep = 0` | 合法，等于关掉撤销能力 |
| 磁盘满 / 文件被占用 | 该文件跳过，其余继续 |
| 目录不存在 | 该目标 `files: 0`，不报错 |
| `journal.db` 损坏 | 判为「不忙」，允许删（该任务已无法续跑） |
| `webview\` 不存在 | `webview.bak-*` 一律不碰 |
| 一次要删超过几万个文件 | 逐个删、失败跳过，首次可能慢，之后不再出现 |
