# 测试清单

没有测试框架，全是能直接跑的脚本：`py -3 _test_xxx.py`，打印 PASS/FAIL，退出码非 0 表示有失败。
每个脚本自己起进程、自己收尾，不需要手工准备环境。

## 五个回归脚本

| 脚本 | 测什么 | 解释器 | 耗时 |
|---|---|---|---|
| `_test_cache_fix.py` | 缓存清理能报出「哪个文件 + 什么原因」 | 3.11 / 3.14 都行 | ~5 秒 |
| `_test_tray_fix.py` | 源码版：自启静默、单实例、事件唤醒、托盘钉子 | **必须 `py -3`** | ~40 秒 |
| `_test_exe.py` | 打包版：同上，打在真 exe 上 | `py -3` | ~50 秒 |
| `_test_close_choice.py` | 源码版关窗三态 | `py -3` | ~40 秒 |
| `_test_exe_close.py` | 打包版关窗三态 | `py -3` | ~40 秒 |
| `test_migrate_engine.py` | 迁移引擎单元测试 | 任意 3.x | 秒级 |

> **为什么源码版必须 `py -3`**：只有 3.14 那个环境装了 `pystray`。用没有 pystray 的
> 解释器跑，托盘起不来，代码会走「关闭即退出」兜底分支，测试会因为「预期进托盘却退出了」而误报。

## 各脚本的具体断言

### `_test_cache_fix.py`

真实造三类失败，不 mock：

1. **只读文件**（`chmod 444`）→ 断言 `_clear_readonly` 去掉只读位后**真的删掉了**
2. **被独占打开的文件**（`CreateFileW` 用 `share=0` 锁住）→ 断言删除失败、失败明细里能定位到
   这个路径、原因文本含 `WinError 32`
3. **嵌套在被独占目录里的文件** → 断言报出的是最里层那个卡住的文件，不是上层目录

另外断言 `_fail_reason` 对 32 / 5 / 未知码都有中文兜底，以及 `run_clean_cache`
在日志里写失败明细（回归「只报个数、查不出原因」的老问题）。

### `_test_tray_fix.py`

| 检查点 | 断言 |
|---|---|
| A | `autostart_cmd()` 以 `--tray` 结尾 |
| B | `--tray` 启动后新窗口存在但 `visible=False`（不弹窗） |
| C | 重复启动第二个实例退出码 0，进程数不变 |
| D | 正常启动的第二次也会退出，但第一个实例窗口被**叫出来**（命名事件生效） |
| E | 源码里没有 `promote_tray_icon`、没有 `unpin_tray_once`，有 `apply_tray_pin` 与 `tray_pin` 三态，写完会读回校验 |
| F | 测试进程全部退出，不留残留 |

### `_test_exe.py`

打在打包产物上，覆盖 A–D 同样的四点，外加「`IsPromoted` 不被写回 1」。

**注意 onefile 的进程数**：一个逻辑实例 = **2 个 PID**（父引导器 + 子进程），
比较进程数要按 +2 算，否则会误判。

### `_test_close_choice.py` / `_test_exe_close.py`

四个场景，跑完会把 `settings.json` 还原：

| 场景 | 预期 |
|---|---|
| A 首次关窗（`close_choice_made=false`） | 弹「关闭方式」；关掉询问窗 → 主窗口隐藏、进程存活、记住为 tray |
| B 已选 tray | 直接隐藏，不再问 |
| C 已选 exit | 进程真的退出 |
| D 已选 ask | 每次都问 |

## 手工验证（脚本覆盖不到的部分）

1. `TIDY_TAB=6 py -3 tidy.py` 进设置页：五个分组默认**收起**，点标题能展开／收起
2. 点右上角 ×，询问窗里**直接按回车** → 应当是「最小化到托盘」，不是退出
3. 托盘图标右键 → 打开主界面；再点托盘 → 退出
4. 托盘图标位置三态：设置里选「跟随系统」→ 手动把图标拖进 `^` → 重启 → 图标应当**仍在**
   折叠区里；改选「始终显示在任务栏」→ 重启 → 图标应当出现在任务栏上。
   `数据	ray.log` 末尾能看到 `tray_pin mode=... try=1 wrote=1 bad=[]`
5. 桌面放一个 `新建文本文档.txt` → 扫描预览 → 开始整理 → 应当出现 `文本\` 子目录；
   撤销上次 → 文件回到桌面
6. 缓存清理跑一次 → 看 `数据\缓存清理.log` 末尾有没有 `    ! <路径>  <- <原因>` 行

## 打包前后的固定流程

```bash
py -3 -m py_compile tidy.py
py -3 _test_cache_fix.py
py -3 _test_tray_fix.py
py -3 _test_close_choice.py
# 打包
py -3 _test_exe.py
py -3 _test_exe_close.py
```

## 跑测试前的清场（重要）

上一次测试留下的残留实例会占着单实例互斥体，导致新一轮「启动即静默退出」，
表现为一堆莫名其妙的 FAIL。先清场：

```bash
powershell -NoProfile -Command "Get-Process | Where-Object { \$_.ProcessName -like '*整理*' } | Stop-Process -Force"
```

源码版残留是 python 进程，按命令行过滤：

```bash
powershell -NoProfile -Command "Get-CimInstance Win32_Process | Where-Object { \$_.CommandLine -like '*tidy.py*' -and \$_.Name -like 'python*' } | ForEach-Object { Stop-Process -Id \$_.ProcessId -Force }"
```

## 在工作区内跑 exe 测试会失败（环境问题）

`D:\Tool\整理助手` 这个目录下的 onefile exe 现在起不来，报
`Could not create temporary directory!`（旧版 exe 也一样）。这是当前 DSH 会话
给工作区施加的沙箱状态，不是代码问题。要跑 `_test_exe.py` / `_test_exe_close.py`，
先把 exe 拷到一个普通目录再跑，例如：

```bash
mkdir -p /d/Tool/apprun && cp 整理助手.exe /d/Tool/apprun/
cd /d/Tool/apprun && py -3 /d/Tool/整理助手/_test_exe_close.py
```

脚本里读的是 exe 自己所在目录下的 `数据\配置\settings.json`，所以带一份配置过去
就能控制测试场景。详见 `打包与发布.md` 的「已知环境坑」。
